# ClassRelay 검증 기록

[English](verification.md)

## 여기서 "검증"이 뜻하는 것

이 기록은 뭉뚱그려지기 쉬운 세 가지를 구분한다.

- **실배포 대상 실측** — 배포된 Worker에 실제 요청을 보내고 응답을 읽었다.
- **실장비에서 관측** — 실제 교육 장비에서 사람이 동작을 확인했다.
- **미검증** — 그 밖의 전부. 자동 테스트가 덮고 있는 동작도 여기에 들어간다. 테스트가 모두 통과했다는 것은 코드가 테스트에 적힌 대로 동작한다는 뜻이지, 제품이 동작한다는 뜻이 아니다.

자동 테스트 결과는 셋 중 어디에도 속하지 않으므로 맨 뒤에 따로 적는다.

## 실배포 대상 실측

2026-09-18, 전용 서브도메인에 배포된 Worker를 대상으로 실제 자격증명을 써서 수행했다. 계정 ID·호스트명·토큰은 여기에 기록하지 않는다.

**인증·역할·제어 소켓 — 9건.**

| 검사 | 결과 |
|---|---|
| 인증 없는 `GET /health` | 200 |
| 자격증명 없는 `/api/*` 요청 | 401 |
| 잘못된 bearer 토큰 | 401 |
| 강사·학생으로 각각 `GET /api/state` | 둘 다 200, 학생에게는 명단이 가려짐 |
| 학생이 mode 변경 시도 | 403 |
| device ID 헤더가 없는 학생 토큰 | 401 |
| 다른 학생의 device ID와 함께 제시된 학생 토큰 | 401 |
| upgrade 헤더 없는 `GET /api/connect` | 426 |
| upgrade와 함께 강사·학생으로 `GET /api/connect` | 101, 각 소켓의 첫 프레임이 상태 프레임 |

**ICE·TURN — 12건.** STUN, TURN 세 가지 전송 방식(UDP·TCP·TLS), 응답이 항상 배열로 오는 점, 연속된 두 요청의 자격증명이 서로 다른 점, 영구 TURN 키가 어떤 응답 본문에도 나타나지 않는 점을 포함한다.

**TLS.** 전용 서브도메인에서 정상 검증된다.

**SFU 협상 순서.** offer는 세션 생성과 함께 올라가고 answer는 같은 응답으로 돌아온다. `{sessionDescription: {type: "offer", sdp}}`를 실은 `POST /sessions/new`는 `201`과 answer를 반환했고, `sessionDescription`이 없는 body는 `400 decoding_error`로 거절되었다. 공개된 Cloudflare 스펙은 반대 순서를 기술하며 낡았다. 그대로 구현한 탓에 화면 송출이 매번 첫 호출에서 실패했다. 실측한 형태는 백엔드 테스트 fixture에 encode되어 있다. 요청·응답 표는 [통신 규격](protocol.ko.md)에 있다.

**`/tracks/new` 쪽은 검증하지 않았다.** 이를 확정하려던 시험은 DTLS fingerprint와 ICE candidate가 쓸 수 없는 합성 SDP를 썼다. 그래서 SFU가 성립하지 않는 전송을 기다렸고 Worker 자신의 10초 시간 초과가 502를 반환했다. 이는 SFU의 거절이 아니라 클라이언트 쪽 산물이다. `/tracks/new`에도 `sessionDescription`이 필요하거나 반환되는지는 여전히 알 수 없다.

## 실장비에서 관측

**강사 1대에서 학생 1대로의 화면 송출이 동작했다.** 강사 1명, 학생 1명, 한 방향이다.

**2026-09-22, 강사 노트북 1대와 학생 노트북 1대, 현재 빌드.** 결함 3건이 드러났고 앱에서 고쳤다. Worker는 건드리지 않았다.

- **학생 앱 종료 명령이 한 번 프로세스를 남겼다.** 송출은 끊겼는데 `ClassRelay`가 작업 관리자에 남아 있었다. 같은 명령을 Worker에 직접 보내니 `notified: 1`, 소켓은 1초 안에 명단에서 사라졌고 프로세스도 그 뒤 종료됐다 — 서버→앱 경로는 동작하며 멈춘 곳은 Electron의 정중한 종료다. 이제 `app.quit()` 3초 뒤 강제 종료가 따른다.
- **강사 앱이 먹통이 됐다.** 모드 버튼이 반응하지 않고 메시지 줄에는 "서버 연결이 종료되었습니다"가 있었다. 4분간의 `wrangler tail`에는 76건이 있었는데 전부 정상 소켓 2개의 WebSocket heartbeat였고 **HTTP 요청은 0건** — 재접속도, 모드 명령도, `/api/ice`조차 없었다. 강사 앱을 다시 켜니 나았다. 첫 HTTP 호출 전에 끝나지 않을 수 있는 경로는 `getDisplayMedia`뿐이므로, 버튼을 비활성화하는 busy 가드가 버튼을 영원히 붙잡고 있던 것이다. 이제 캡처 호출과 모든 버튼 동작에 상한이 있고(10초·30초), 재접속 시 낡은 끊김 문구를 지운다. 정확히 어느 호출이 멈췄는지는 잡지 못했다. 재발을 막는 것은 상한이다.
- **장비당 `ClassRelay` 프로세스 4개는 정상이다** — Electron 인스턴스 하나가 main·GPU·renderer·utility다. 없던 것은 단일 인스턴스 잠금이라 `run.bat`을 두 번 누르면 같은 장비 식별로 두 번째 프로세스가 뜰 수 있었다. 이제 앱이 잠금을 잡는다.

**실서비스 Worker에 학생 토큰 30개로 180초** (실제 장비가 아닌 합성 소켓): 30개가 2.1초 안에 접속했고, 표본 11회 내내 강사 명단은 30/30에 예기치 않은 끊김 0건, 저장된 `lastSeen` 지연은 설계 상한 10초 대비 최대 9.1초, `mediaReady`는 정확히 일치, 소켓 종료 284ms 뒤 명단이 비었다. 같은 장비 ID의 두 번째 접속은 첫 번째를 `1012 superseded`로 닫았다. 강사가 발행하지 않은 스트림으로 `lecture`·`lock`을 요청하면 403으로 거절됐다.

## 미검증

아래는 실장비에서 한 번도 수행한 적이 없으므로 그대로 적는다.

- **Windows 입력 잠금은 한 번도 걸린 적이 없다.** 모든 장비 설정에서 `nativeInputLock`이 `false`라 실제 잠금이 동작한 적이 없다. 지금까지의 잠금 항목은 전부 표시 검사였다.
- **학생 앱 종료는 실장비 1대에서만 실행했다.** 그 뒤 추가한 강제 종료 보험은 아직 실장비에서 발동해 본 적이 없다.
- **송출 중 화면 교체를 실장비에서 시도한 적이 없다.**
- **실제 대역폭을 모른다.** 지금까지 관측한 유일한 값인 1fps에서 약 15kbps는 정지된 슬라이드였다. 이는 유휴 화면의 비용을 말할 뿐 수업의 비용이 아니며 용량 산정에 쓸 수 없다. 문서의 용량 수치는 여전히 계산값이다.
- **실제 30대, 그리고 5시간 soak.** 위의 30소켓 실서비스 soak는 제어 계층만 확인한 것이다. 영상도, 입력 잠금도, 30종의 Wi-Fi도 아니다.
- **로그인 자동 시작.**
- **최근 수정이 보고된 학생 화면 깜빡임을 실제로 없앴는지 여부.** 그 변경은 Agent가 5초 heartbeat마다 창 상태를 다시 적용하던 동작을 멈추게 했고 원인으로 그럴듯하지만, 이후 학생 화면을 본 사람이 없다.

운영 전에는 [실제 장비 검증표](acceptance.ko.md)를 수행한다.

## 자동 테스트와 CI

- 백엔드 73개, 데스크톱 앱 143개 통과. 백엔드 타입 검사와 앱 구문 검사도 통과한다.
- 기본 브랜치의 CI는 통과 상태다. 백엔드 테스트, 백엔드 typecheck, 앱 테스트, 앱 구문 검사, 로컬 30연결 WebSocket 스모크 테스트, 네이티브 helper 빌드, `InputGuard.exe --self-test`, Worker 배포 dry-run을 돌린다.
- 네이티브 helper는 `--self-test`로만 확인한다. 이는 실제 입력 hook을 설치하지 않고 상태만 갱신한다. 실제 입력을 억제한 적은 없다.
- 백엔드의 SFU 호출은 테스트에서 mock한다. 세션 생성 부분의 mock은 실측한 라이브 계약과 일치하지만 `/tracks/new` 부분은 가정이며 테스트 파일에 그렇게 적혀 있다. 현실과 다른 mock은 전부 통과한 테스트 뒤에 동작할 수 없는 제품을 숨긴다. 세션 생성 순서에서 실제로 그 일이 일어났다.

## 과거 로컬 검사 (기록)

실배포가 존재하기 전인 2026-09-17, Windows 개발 환경에서 수행했다. 아래 개수는 당시 기록이며 이후 늘었다.

- 로컬 workerd 통합 검사(`node scripts/ws-smoke.mjs`)에서 강사 1개와 학생 30개의 모의 WebSocket 연결이 통과했다. SFU 소유권만 로컬에 테스트용으로 등록했으며 실제 영상은 보내지 않았다.
- 잠금·실습 상태 일괄 전달, 학생 명단 비공개, 학생 heartbeat가 계속되는 동안 강사 무응답 15초 후 해제, 만료 잠금 복원 방지, 강사 연결 교체·종료 시 해제를 확인했다.
- 최종 로컬 실습 전환 전달 시간은 약 10ms였다. 개발 PC에서 관측한 값이며 인터넷 환경의 지연 보장이 아니다.
- 네이티브 helper 재빌드와 `--self-test`가 통과했다. 실제 Windows 입력 hook은 실행하지 않았다.
- `npm.cmd run dist --prefix apps -- --config.compression=store` 패키징에 성공했다. 패키지 안 JavaScript와 최종 소스가 일치했다. 해당 로컬 빌드는 압축을 끈 상태이며 실행 파일은 서명되지 않았고 실제 입력 제어를 켠 채 실행한 적이 없다.
- 통합 검토 중 HTTP 200 응답 안의 개별 SFU 트랙 오류를 등록 성공으로 취급하는 결함을 발견해 수정하고 회귀 테스트를 추가했다.
